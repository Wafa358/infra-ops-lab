# Postmortem: web1 stops serving (incident drill 1)

| | |
|---|---|
| Date | 2026-11-23 |
| Type | Planned drill (fault injected on purpose) |
| Duration | About 3 minutes, 12:10 to 12:13 UTC |
| User impact | None: every request was answered |
| Author | Wafa |

## Summary

Nginx was stopped on `web1`, one of the two web servers behind the load balancer `lb1`.
HAProxy took `web1` out of the pool within seconds and sent all traffic to `web2`, so the
site kept answering. The health check on `web1` reported the cause, and starting Nginx
again brought `web1` back into the pool about 5 seconds later.

## Timeline (UTC)

| Time | Event |
|---|---|
| 12:10 | Fault injected: `systemctl stop nginx` on `web1` (time to the minute; the exact second was not recorded) |
| within ~4 s | HAProxy health checks fail twice, 2 seconds apart; `web1` is marked DOWN |
| 12:11:08 | Check from outside: 6 of 6 HTTPS requests answered, all by `web2`; the stats page shows `web1 DOWN`, `web2 UP` |
| 12:11 | Health check on `web1`, run by hand: CRITICAL, `nginx is inactive` and `/health did not answer` (the 5-minute timer would have caught it by 12:15 at the latest) |
| 12:12:56 | Fix: `systemctl start nginx` on `web1` |
| 12:13:01 | Stats page shows `web1 UP`; the health check on `web1` passes again |

## Impact

None seen by users. The load balancer kept serving from `web2`, which had enough
capacity for the lab's traffic. With one web server left, a second failure during
the incident would have taken the site down.

## Detection

| Layer | How it noticed | How fast |
|---|---|---|
| HAProxy | `GET /health` every 2 s, 2 failures mark a server DOWN | about 4 s |
| `healthcheck.timer` | Service and endpoint checks every 5 minutes; the run fails and logs CRITICAL | up to 5 minutes |

## Root cause

Planned: Nginx was stopped on purpose to test failover and detection. In a real incident
the same symptoms would come from Nginx crashing, a bad configuration, or the VM going down.

## What went well

- Failover was automatic, and no request failed.
- The health check named the cause directly (Nginx inactive), not just "the site is down".
- Recovery after the fix took about 5 seconds, with no manual step on the load balancer.

## What went wrong, or could be better

- **Nobody was alerted.** The CRITICAL result stays in the VM's journal; an operator only
  sees it by looking. A real setup sends it to an alerting system.
- **Nginx does not restart on its own after a crash.** A stopped service stays stopped.
- **The first version of this drill lost one request.** It was sent in the 4 seconds before
  HAProxy marked `web1` DOWN, and got an error.
- **The time of the fault was not recorded to the second**, so the exact time to detect is
  an estimate.
